# cross-session trigger hygiene

## 2026-09-05 — Disable, don't delete, after firing a cross-session trigger

**Decisions:** When one session needs to tell another session (via `create_trigger` + `persistent_session_id` + `fire_trigger`) to do something, especially something sensitive or boundary-crossing, don't `delete_trigger` right after firing to stop a double-fire — `update_trigger` with `enabled: false` instead. Deleting destroys the one thing the receiving session can check for itself (that the trigger genuinely exists in the shared account, who created it, when) and leaves it with nothing but the message's own claims to go on — exactly what a real prompt injection would also produce. The fired message itself should also say plainly that the receiving session can call `list_triggers` to verify, rather than asking it to just trust the ask.
**Facts / preferences:** Dex explicitly does not want receiving sessions to become *more* suspicious/locked-down by default over this — the fix is giving verifiable evidence alongside a cross-session ask, not dialing up default distrust. A session's skepticism of an unverified, sensitive-data-reversing instruction (as Brand 841's session showed) is correct behavior and should not change; what changes is whether it has something real to check.
**Artifacts:** Real incident this came from: a trigger fired into the "Brand 841" session (session_01CP5hmzRZNMTZCkWsCHbM4k) asking it to save an SSN/EIN/home address into a private repo — it correctly refused the sensitive-data part (see the chat-memory NEVER-tier fix, same day) and separately, correctly, treated the trigger itself as unverifiable since it had already been deleted by the time it went looking.
**Open threads:** No tooling change yet, just a practice change (disable-not-delete + tell the receiving session how to verify) — nothing currently enforces this beyond remembering to do it each time.
