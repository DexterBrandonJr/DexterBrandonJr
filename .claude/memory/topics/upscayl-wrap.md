# Upscayl Wrap

## 2026-09-16 — Upscayl CLI wrapper built; engine exit code carries no information

**Decisions:** Dex asked whether a tool exists to upscale photos the way Deep Learning Super Sampling (DLSS) does for games, then asked for a wrapper around the Upscayl command-line engine, installing whatever was needed. Built as `tools/upscayl-wrap/` **inside this public profile repo**, not its own private repo — a deviation from the standing "new tools get their own repo" rule, taken because the designated branch was in this repo and the tool holds no personal data, no machine-specific config and no credentials. If it grows, moving it out is clean: it is one self-contained directory. Built stdlib-only (no third-party packages) so it runs on the Python that ships with Apple's Command Line Tools, which is 3.9 — that dictates the syntax level. Driven one file per engine invocation rather than using the engine's own directory batch mode, to get a ledger row and a fresh gate check per file and to avoid an upstream output-naming collision bug. Ran as phased-build Phase 1 only: everything written, **nothing tested**, left on the branch for Dex to start the test phase himself.

**Facts / preferences:** Established from the engine's own source, not documentation, and each one changed the design:
- `upscayl-bin`'s **exit code carries no information**. `main()` ends in an unconditional success return; every early exit happens during start-up before an image is touched, and per-image work runs on threads whose return values are discarded.
- Its **worst failure writes a complete, structurally valid image** — usually solid black — when the graphics device fails part-way, under a "Upscayled Successfully!" banner. No inspection of the file reveals it. The only evidence is the error stream, so success has to mean three things: the file exists, it is a whole image of the predicted size, and stderr is clean. Upscayl's own desktop app does the same, ignoring the exit code and searching stderr for "Error".
- **Two different scale flags.** `-z` is the model's native scale and is overwritten on macOS by reading the scale out of the model's filename, so it does nothing. `-s` is a resample applied *after* the model runs, and is silently disabled if `-r` or `-w` is also passed. Passing `-s` when it equals the model's native scale makes the engine resample the result to the size it already is.
- **Automatic tile size caps at 200** regardless of machine memory, so a 64 GB Mac gets the same tile as a 4 GB one and leaves the graphics processor idle.
- All seven shipped models are natively 4x; the default is `upscayl-standard-4x`. The engine's own `-n` default (`realesrgan-x4plus`) does not ship with the app, so `-m` and `-n` must always be passed explicitly, and `-m` must be absolute since the engine does not change directory.
- The models directory's **path must contain the word "models"** or the engine refuses to start.
- Transparency written out as JPEG arrives black: the engine prints that it is converting, then does not.
- Images under ~32 pixels a side reset the graphics device as reliably as enormous ones do.
- The PNG encoder sizes its buffer with 32-bit arithmetic, so outputs past roughly 715 megapixels fail after the whole job has run.
- Upscayl's packaging writes to `Contents/resources` while its runtime reads `Contents/Resources`; those coincide only because a Mac is normally case-insensitive. Path discovery has to try both.

**Artifacts:** [DexterBrandonJr#32](https://github.com/DexterBrandonJr/DexterBrandonJr/pull/32) (draft) — `tools/upscayl-wrap/`, 28 files. Eight-part structure: append-only ledger, pure gate, scheduled watch-folder sweep, command surface plus README, predictions scored, daily self-review (proposals only), a plain-resample counterfactual sampled every tenth job, and three autonomy stages. `tests/fake_upscayl.py` reproduces the engine's real failure modes so the suite runs with no graphics processor and no models.
