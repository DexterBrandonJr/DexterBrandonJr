# Trading Engine

## 2026-09-07 — Webull options trading system: research, architecture, WIF setup

**Decisions:** Project named `trading-engine`, not `sizeup` -- Dex's explicit call, since the tool is for trading, not just risk-sizing (no security reason to object; repo is private either way). Architecture follows the `csearch` pattern directly: read-only analysis first, autonomous EXITS only as the first automated stage, autonomous entries locked behind a documented positive expectancy over a real sample -- never skip straight to unsupervised entries. `autopatch` may fix plumbing (crashes, API errors, broken parsers) but must NEVER touch risk rules, position sizing, or entry/exit logic -- same boundary as `csearch`'s quarantine.py, enforced structurally (a checksum + failing test on the rules file), not by policy. Dex already has a real, working manual system in Google Drive (a multi-account Webull trade journal with written risk rules, R-multiple/ROI tracking, and per-account risk profiles) -- the tool's job is to encode and enforce that existing system, not invent a new one. Lesson from analyzing his early real trade sample: negative expectancy was driven by average loss exceeding average win at a sub-50% win rate, and a correlated loss across multiple accounts on one ticker violated his own written "no more than 10-15% of liquidity in one trade" rule -- the gap is enforcement, not strategy, which is exactly what a pre-trade gate (portfolio-wide size cap, cross-account correlation check, reward:risk floor, stop-type check) is for. Webull MCP connector (separate from the OpenAPI key) came pre-authorized for Trading on all 6 accounts; Dex's call: "MCP will be a backup, we'll work from API first" -- MCP is not the primary execution path.
**Facts / preferences:** Webull allows only ONE OpenAPI application per developer account (confirmed by testing -- "Apply for API Keys" just routes back to the existing key, not documented anywhere by Webull). Dex granted the one application (`Trading Engine`) BOTH Market Data and Trading permissions rather than starting Market-Data-only as I'd suggested -- since a second, permission-split key isn't possible, the read-only/trading-capable boundary has to be enforced entirely in code from day one, same mechanism as the autopatch boundary above. Claude Console org is on the free "Evaluation access" plan with $0.00 credits and no billing set up -- Workload Identity Federation (WIF) authentication succeeds and mints a real bearer token regardless, but an actual `messages.create()` call will still fail until billing is configured. That's the next known blocker, not yet resolved.
