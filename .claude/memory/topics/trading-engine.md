## 2026-09-07 — Build step 1 shipped: protected risk rules + circuit breaker, draft PR #1

**Decisions:** Two design calls made while building that weren't in the plan and are worth keeping. First, `ALL_RULES` (the registry of which rules run) lives inside the protected rules file rather than in the orchestrating gate -- otherwise dropping a rule would need no protected file touched, which defeats the guardrail entirely. A test also asserts every `rule_*` function defined is registered, so a rule can't be written, tested, and left dead. Second, domain dataclasses live in an unprotected `models.py` while policy lives in the protected file, so adding a field never rewrites the rules -- the boundary being "shapes are not policy," documented in both files. Also settled: the guardrail is two independent layers, not one. A checksum catches any change at all (and forces the regenerated manifest into the same diff, which is the actual point -- visibility to a reviewer, not cryptographic security, since whoever edits the file can also regenerate the manifest); an AST purity check separately enforces invariants that must survive a *legitimate* checksum-updated edit (no network, no I/O, no order placement in a policy file).
**Facts / preferences:** Verified the guardrails against real tampering rather than only synthetic test doubles -- widening the size cap back to 15% was caught by the checksum, adding `urllib` to the circuit breaker was caught independently by both layers. This is the direct application of the earlier lesson in this project that a green checkmark can be misleading: a guard only observed passing is indistinguishable from a guard that cannot fail, so every guard has a test that makes it fail on purpose. The one confirmed real-world failure in Dex's trade history (same ticker held across three accounts) is now reconstructed as a named test that the ticker and thesis rules both refuse.
**Artifacts:** `DexterBrandonJr/trading-engine` draft PR #1 (branch `claude/gate-rules-and-kill-switch`): `gate/rules.py`, `kill_switch.py`, `models.py`, the `tests/guardrails/` machinery with a manually-run checksum updater, and CI on Python 3.11-3.13 including a job proving the core install pulls no third-party packages. 88 tests, stdlib-only. ## 2026-09-07 — Build step 2 shipped: read-only Webull clients; OTOCO confirmed in the real SDK

**Decisions:** Use Webull's official Python SDK for request signing rather than hand-rolling it. Webull signs every request with HMAC-SHA256 over a canonical string; writing that by hand would mean guessing at a format only verifiable against a live credential, where a subtly wrong signature is a 401 with nothing to debug. This is the opposite call from the csearch MLX adapter and for a good reason -- there, no alternative to guessing existed; here the vendor ships the implementation. The SDK is an *optional* extra, not a hard dependency, and exactly one module (`data/session.py`) imports it, so every other module tests with no vendor package, no credential and no network. Second decision: read-only is structural, not documented. The SDK's order object carries `list_open_orders` next to `place_order`, so the client holds it privately, forwards no attributes, and hand-writes every method.
**Facts / preferences:** Introspected the installed SDK rather than trusting doc summaries, which confirmed the two facts the whole architecture rests on: `ComboType.OTOCO` exists (the bracket order behind "works with the laptop offline and phone off") and so do `OrderTIF.GTC` and `OrderType.STOP_LOSS_LIMIT` -- the last one matters because the AG catastrophic fill was a *market* stop, and the limit variant is the fix. Also confirmed `place_order` takes a `client_order_id` (the idempotency key the plan assumed) and that `TrailingType` exists for the Stage 2 trailing-stop work. Response payloads are returned as the API shaped them: mapping them onto our models needs real field names, which take one live call to confirm, and guessing would produce a parser that looks right and silently mis-reads a balance.
**Artifacts:** `DexterBrandonJr/trading-engine` PR #2 (`claude/webull-read-only-clients`): `data/` with credentials (env-only, masked repr), a per-category sliding-window rate limiter matching Webull's documented limits, shared transport that turns a non-2xx into an exception exactly once, and the two read clients. 129 tests. ## 2026-09-08 — Build step 5: horizons, calibration, setup detection; QA found a fabricated catalyst

**Decisions:** Dex asked for a predictive index reaching from one week to five years and beyond. The position taken, and worth holding to: the useful half is real (tag every source with the distance it actually describes and refuse it outside that range -- options flow expires in weeks, the insider research measures six to twelve months, macro turns over quarters), and the other half needs saying rather than quietly implementing. Nothing at any price supports an actionable forecast of a specific instrument two to five years out, and options expire long before such horizons resolve, so those horizons exist in the model carrying sizing context and never trade ideas. A `context_only` flag separates "what distance does this describe" from "may this generate a trade" -- macro genuinely speaks to the quarter but must not produce a card. Second decision: calibration is what turns "predictive" into a measurement. Below thirty samples the system returns no rate at all -- `None`, never a low-confidence number, so a caller cannot mistake "we don't know" for "50%". Above it the rate carries a Wilson interval and ranking uses the *lower bound* rather than the point estimate, because six hits from ten looks like a 60% edge while its interval runs 31-83% and comfortably contains worse-than-chance.
**Facts / preferences:** The QA/QC pass found five real defects, each reproduced with a probe before being fixed, and one of them is the kind worth remembering as a pattern rather than an incident: setup detection was *fabricating a catalyst date* (`now + horizon/2`) whenever no real event was scheduled, which meant code downstream of the gate was manufacturing the very thing the gate's catalyst rule exists to demand. A safety rule that downstream code can satisfy with invented input is not a safety rule. The general lesson: when one layer enforces a constraint and another layer constructs the input to it, check whether the second can trivially satisfy the first. The other four: thesis keys built from detector kinds alone collided unrelated tickers into a single correlation ceiling; one evidence set produced a separate setup at every shared horizon, making one observation look like several opportunities; a `strategy` parameter was accepted and silently ignored; and a single contract labelled a debit spread slipped past an account permission check and skipped the naked-premium advisory. Honest labelling restored both checks.

## 2026-09-08 — Build step 6: cards and execution; the re-probe habit caught an incomplete fix

**Decisions:** The decision card reproduces Dex's own "Kill Card" format rather than inventing a layout -- Scenario A is the trade, Scenario B is standing down, both decided before the open. That choice is deliberate: the format he already trusts is the one he will actually read on a phone between calls, and a card that shows only the case *for* a trade is an advertisement, so anything the gate flagged prints beside the trade. Second: an approval is bound to a card *fingerprint* (a hash over account, ticker, contract, strategy, size, all three bracket prices and expiry), so changing the strike, the size or the stop means the approval simply no longer matches -- an approval cannot be replayed onto a different trade, and it expires after four hours because an approval is a statement about conditions at a moment. Third: execution re-runs the gate against the portfolio *as it stands at placement*, not the verdict printed on the card, since another account may have taken the same thesis past its ceiling in the interim. Fourth: the client order id is derived from the fingerprint rather than random, so a retry after a timeout is rejected by the broker as a duplicate instead of filled twice. Fifth: no leg is ever a market order -- entry is a limit, the stop is a stop-limit -- because the one catastrophic fill on record was a market stop in a liquidity gap.
**Facts / preferences:** The QA/QC pass found four defects, two of which would have placed a real order, and one is worth keeping as a *habit* rather than an incident. The gate re-check originally validated a trade passed in as a separate argument from the card, so a benign one-contract candidate could satisfy every rule while the card placed a large position in a different ticker entirely. My first fix was to move the trade onto the card, and I described that as structural. Re-running the original probe verbatim -- rather than trusting the fix -- showed it was still broken: a card could be constructed holding a trade that described something else. The card now asserts its own account, ticker, size and expiry agree with the trade it carries. That is the second time on this project that a fix I called "structural" needed the original probe re-run to prove it, and re-probing rather than re-reasoning is becoming the most valuable habit here. The other three: an approval dated in the future never expired (a negative age passes an upper-bound-only freshness check, so the fix was a lower bound at zero); a stop at or above the entry was placed without complaint, which triggers the moment it fills; and a zero- or negative-contract order was placed without complaint.

## 2026-09-09 — Webull 401 solved: two causes, both ours

**Decisions:** The first paper attempt died at the first command on `401 Unauthorized`. My first two readings were wrong -- I said it was an entitlement/permission problem and pushed contacting Webull support. Dex overruled that twice, the second time explicitly: *"i dont want you to push back on troubleshooting on our end and solving this error"* and *"assume it's something we messed up."* He was right both times. The correction that actually worked was to stop hypothesising and build a diagnostic that asks the server (`scripts/check_webull_auth.py`): shape-check the credentials without ever printing them, compute the signature two independent ways, compare both against the worked example in Webull's own published docs, then send one harmless `GET /openapi/config` each way and report which the server accepted. Every hypothesis after that one was correct. Standing lesson, and the reason this entry exists: on a failure whose symptom is "you lack permission," build the instrument before proposing the cause -- and when the user says the fault is probably ours, believe them and go look. Also decided: the SDK is patched at the one function that is wrong, not forked and not wrapped -- `use_documented_signing()` replaces `_refresh_sign_headers` with the SDK's own implementation and one constant changed, is idempotent, and is called by `build_api` before any client exists so no caller has to remember it.
**Facts / preferences:** TWO independent causes, both ours, either alone enough to produce the same 401. (1) The app secret had gained one character in transcription -- 33 where 32 belong, invisible by eye, indistinguishable from a permissions failure at the server. The shape check catches this class without ever displaying the value. (2) `webull-openapi-python-sdk` signs **HMAC-SHA256**; this server accepts only the documented **HMAC-SHA1** over an **MD5** body digest with the secret suffixed `&`. It cannot be fixed by passing an argument -- `default_signature_composer._refresh_sign_headers` hardcodes `signer_spec = sha_hmac256_new`, overwriting whatever the caller passed. The body hash matters as much as the HMAC: `_get_body_string` picks MD5 vs SHA-256 off the signer it is handed and `calc_signature` uses the *returned* signer for both, so a patch that switched the HMAC and left the body hash would have authenticated every read and rejected every order -- surfacing first at the moment a trade is placed. A THIRD trap sits just past those: `account_id` (long opaque string) and `account_number` (the short code the portal shows) are different things, and passing the number where the id belongs returns `403 ACCOUNT_ACCESS_DENIED` -- which also reads as a permissions problem and also isn't one. Ruled out, so don't re-investigate: 2FA (off, and Webull's docs say test-environment tokens are valid on creation -- the sandbox confirms it with `token_check_enabled: false`); entitlement/binding (the "empty array" that suggested it was the Mac session's own `grep -v "^ "` deleting indented JSON); the `oauth-open-api.sandbox.webull.com` host; and "keys missing from the repo/Supabase/Vercel" (there is no Vercel in this project, and the Webull credential must never go in either). `--list-accounts` had never worked at all -- it called `account.get_app_subscriptions()` on `/app/subscriptions/list`, a route family with no `/openapi` prefix that 404s on the sandbox; `account_v2.get_account_list()` is the one that answers.
